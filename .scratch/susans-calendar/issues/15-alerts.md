# 15: Alerts

**What to build:** When a text to Susan does not get through, every Admin is told by email and by app notification, with enough detail to know what to say when they call her. While the problem stands, a banner shows on every screen of the app. Susan never receives Alerts.

**Spec:** `.scratch/susans-calendar/spec.md`, section "Alerts and Activity updates"; user stories 61 to 65, 67, 68.

**Blocked by:** 08 (App notifications and Activity updates), 11 (Sending texts on schedule).

**Parallel:** Yes, with 13, 14 and 16. It does not wait for Textbelt: an Alert is raised for any text that reaches a failed or not-sent status, whatever caused it, so the failures ticket 13 introduces raise Alerts without further work.

**Status:** done

- [x] Susan never receives an Alert by either channel.

## As built

- **The email channel.** The Admin messenger port (`AdminMessenger` in `src/lib/calendar/ports.ts`) gains `sendEmail`. In the backend (`amplify/calendar/admin-messenger.ts`) it lists the `Admins` group for each Admin's sign-in address and emails each one on their own through SES's v2 `SendEmail` (`amplify/calendar/alert-email.ts`), from `ALERT_EMAIL_FROM`, set at deploy. A person ID that is not an Admin's reaches no address. The adapter spaces emails a little over a second apart, tries again when SES is busy or does not answer (up to three tries), and treats any other refusal, such as `MessageRejected` for an address the sandbox has not verified, as final. It logs only the error's name. Without `ALERT_EMAIL_FROM`, no email is sent, Alerts go by app notification only, and the scheduled run is given no SES permission. It is tested against synthetic SES answers; nothing reached AWS.
- **The sandbox question.** AWS's documentation, checked on 20 November 2026, says the SES sandbox sends from verified identities to verified addresses, 200 a day and one a second, per region. That is enough, so the fallback is not used. The spec says so, and the README's "Alert emails" lists the owner's steps: verify the sending address and each Admin's address in the app's region, set `ALERT_EMAIL_FROM`, and try it once by hand. An email has not yet been sent for real; that is the owner's live test.
- **Permission.** The SES v2 Service Authorization Reference (`list_sesv2.html`) lists `ses:SendEmail` on the `identity` resource, with the `ses:FromAddress` condition key. The scheduled run may call only that, with the From address equal to `ALERT_EMAIL_FROM`, on identities in its own account and region. `npm run synth` builds with a synthetic sender and checks the action, the condition, the account and region, and that no other role may use SES.
- **Routes.** `alertMarked` (`src/lib/calendar/alerts.ts`) marks a text's Alert due in the same write that settles its record as failed (any reason), or as not sent with the reason `tooLate` or `noNumber`. Every write of a text's record in the core goes through it, so failures from other tickets raise Alerts with no further work. A Reminder not sent only because no number was set is told apart from one that could not be sent in time and from a failure, in words about what happened then. A failed test text raises one, linking to Settings; the command marks it and the next scheduled run sends it. A text recorded before this ticket raises none, so old failures do not flood the Admins after the deploy.
- **With ticket 13.** A text's record gains `alert` (null, or its state, tries, last take-up and the deliveries sent) beside 13's `creditLeft`; the reasons `undelivered` and `unconfirmed` are 13's and mean the same here. 13's status poll now turns the sender's report (and its `unconfirmedAfter` period) into the provider-neutral outcomes `delivered`, `undelivered` and `unconfirmed`, and settles each text through `deliveredText` by the store's conditional `changeText`, once, instead of an unconditional replace; `recordDelivery({ textId, outcome })` makes the same transition from outside the run. The poll still asks a few at a time (`STATUS_READS_AT_ONCE`) and records each answer as it comes; the Alerts it marks are sent after the whole poll, one delivery at a time, so SES's spacing holds and a slow answer delays only the Alerts, not other answers. A text 13 records as not sent because its words hold a web address raises its own Alert (`webAddress`), worded apart from failures and missing numbers, never repeating the address; the banner says so too.
- **Each delivery once.** The messenger names each delivery (`email:<person ID>`, `app:<device ID>`) and reports which went, which failed and may go if tried again, and which were refused for good; a person with nothing to reach on a channel has none, which is not a failure. The run takes the Alert up by a conditional write (`sending`, with the moment), sends one Admin and one channel at a time, leaving out what already went, and records each that went before the next. If any failed, the Alert is due again two minutes on (`RETRY_AFTER`), and after three tries (`ALERT_ATTEMPTS`) what still fails is given up and logged. A run that stops part way leaves the Alert held; once it has been held longer than any run lasts, a later run takes it over and sends only what was not recorded. The one repeat that can happen is a delivery that went just before a run stopped, before it was recorded. Tests cover a failure on one channel to one Admin, a delivery that keeps failing, a refused and an unreachable one, email failing outright, nobody being reachable, overlapping runs, and a run that stops mid-way.
- **Words.** The core writes them (`alertFor`): the Appointment's name, date and time, the text's kind and when it was due, and why. Nothing else of the Appointment, nor Susan's number, nor the text's words. The email ends with the Appointment's address in the app, added by the messenger from `APP_URL`; a sandbox, with no app address, gets no link. The app notification opens the Appointment, or Settings for a test text, tagged by the text so that one Alert never replaces another.
- **The banner** (`src/components/TextsBanner.tsx`) shows at the top of every screen, at both widths, while `textTrouble` finds that the most recently tried text that has settled, of any kind, did not get through. It says what happened to that text, so a missing number is described in the past and stays true once the number is entered. It links to the Appointment, or to Settings for a test text or a missing number. A later text that is sent or delivered clears it.
- **Backend.** The scheduled run gets the real Admin messenger and may list the `Admins` group. `npm run synth` checks that, the SES permission, and that an Alert is taken up and recorded only by conditional writes. The `Text` model gains `alert`, `alertTries`, `alertTriedAt` and `alertSent`, flat so that a write can be conditioned on them.
- **Glossary.** `CONTEXT.md`'s Alert now covers any text to Susan, test texts included, as the gate on this ticket asked.
- **For the owner to decide:** whether a Reminder not sent only because Susan's number was not set should raise an Alert at all, or only show the banner. It raises one now, worded as a setup problem. Before ticket 18 this means an Alert for every Reminder that comes due while no number is entered.
